# Smart task reminders — product rules

This document captures the reminder behavior for the Telegram + Supabase + Claude task system. Use it as the source of truth when implementing reminders.

## Goals

- Send **smart reminders** during the day about **tasks that are still open**.
- Reminders are **only sent during genuine free time** inferred from **Google Calendar**.
- Reminder **copy is composed by Claude** (Anthropic API), consistent with the existing task assistant pattern.
- Scheduling runs in the **existing Node process** (e.g. `node-cron`); **do not use Trigger.dev**.

## Global limits

- **Maximum 3 reminders per calendar day** (reset at a defined boundary, e.g. midnight in America/New_York, or document whichever you choose at implementation time).
- **At least 2 hours** must pass between the send time of **any two** reminders (wall-clock).

## Time window for sending

- Reminders may be sent **only between 12:00 (noon) ET and 22:00 (10:00pm) ET**, inclusive of the window boundaries as implemented (document exact inclusive/exclusive semantics in code comments).
- Timezone for this window: **America/New_York** (handles EST/EDT).

## Google Calendar — what counts as “busy”

- Use **Google Calendar** data to determine **free gaps** in the user’s schedule.
- **Minimum free gap length:** **30 minutes** (time until the next calendar busy block, or the fetch horizon if none sooner). Shorter gaps are **not** eligible for a reminder (treat as non-free for reminder purposes).
- **All-day events:** **Ignore** — do **not** treat all-day events as blocking time when computing free gaps.
- **Declined events:** **Ignore** — do **not** treat events the user has **declined** as blocking time when computing free gaps.

## When a reminder is allowed (eligibility)

- Whenever there is a **calendar gap** (per the rules above), determine **how many minutes remain in that gap from “now”** (or from the evaluation instant used by the cron tick—document at implementation).
- Consider **only open tasks** from Supabase (same notion of “open” as the rest of the app).
- A task is **eligible for suggestion** only if its **estimated duration** (minutes) is **≤ the remaining minutes in the current gap** (i.e. what could **realistically be accomplished right then** in that gap).
- The reminder should be **based only on what can be accomplished right then**: suggest **concrete work the user could do now** grounded in tasks that **fit the current gap**, not a generic dump of all open tasks.

## Content

- The **reminder message** is **generated by Claude**, given structured context (e.g. gap length, candidate tasks with title + duration, prior constraints like tone).
- Implementation should keep **scheduling, gap math, caps, and spacing** in **deterministic code**; Claude only **phrases** the message within those constraints.

## Persistence

- Persist reminder sends (timestamps and optionally message/task metadata) in **Supabase** so that:
  - the **3-per-day** cap survives process restarts;
  - the **2-hour minimum** between sends is enforceable;
  - behavior is debuggable.

## Out of scope / explicit non-decisions (clarify at implementation if needed)

- Exact **cron frequency** (e.g. every 5–15 minutes during the send window).
- Whether “remaining gap minutes” is measured at tick start vs after small buffer (e.g. travel/setup time).
- How to handle tasks with **no** eligible task in a gap (no reminder vs. motivational nudge—default: **no reminder** unless product says otherwise).
